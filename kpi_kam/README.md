# KPI KAM — desktop GUI

Существующее приложение расширено общим файлом продаж, отдельным внешним
прайсом, сотрудниками и должностями на год, возвратами FIFO, выплатами,
KAM/SUPPORT и административным режимом. Расчеты используют прежнее
протестированное Decimal-ядро через новый monthly policy layer.

Пошаговая работа: [RUNBOOK.md](RUNBOOK.md).
План и свойства миграции существующей БД: [MIGRATIONS.md](MIGRATIONS.md).
Нерешенные сопоставления приложенных продаж: [MANUAL_REVIEW.md](MANUAL_REVIEW.md).
Начальный список дополнен **Филимоновой Анной**; менеджер **«тендер»** исключается.
Никаких догадок по товарам, должностям или неизвестным менеджерам.
Требования: Python 3.12+, PySide6, SQLite, openpyxl, pytest, PyInstaller.

## Установка и тесты

Из каталога `kpi_kam`:

```sh
python -m venv .venv
# Linux/macOS
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest -q
.venv/bin/python main.py
```

На Windows замените `.venv/bin/python` на `.venv\Scripts\python.exe`.
`main.py` без аргументов открывает GUI. `main.py gui --db PATH` позволяет
задать другую папку данных. `main.py demo` запускает искусственную демонстрацию
ядра. Команды `check` и `calculate` сохранены для работы без GUI (см. ниже).
После установки pytest тесты и ядро работают без интернета и Microsoft Excel.

## Windows-сборка PyInstaller (onedir)

Для сборки нужны **Windows x64 и Python 3.12 x64** с Python Launcher (`py`).
Скачивание зависимостей требует интернета; готовое приложение работает без
Python, Microsoft Excel и интернета. Версии PyInstaller и Qt зафиксированы
в `requirements-build.txt` и `requirements.txt`.

Из корня клонированного репозитория, в **cmd.exe**:

```bat
cd kpi_kam
build_windows.bat
```

В **PowerShell**:

```powershell
Set-Location kpi_kam
.\build_windows.bat
if ($LASTEXITCODE -ne 0) { throw "Windows build failed" }
```

Если Python Launcher не установлен, перед запуском задайте абсолютный путь
к Python 3.12 x64 (пример для cmd.exe):

```bat
set "KPI_BUILD_PYTHON=C:\Python312\python.exe"
build_windows.bat
```

Скрипт работает из своего каталога, создает отдельную `.venv-build`,
устанавливает зависимости, запускает все pytest-тесты и выполняет:

```bat
.venv-build\Scripts\python.exe -m PyInstaller --noconfirm --clean --distpath dist --workpath build\pyinstaller KPI_KAM.spec
.venv-build\Scripts\python.exe tools\smoke_frozen.py --executable dist\KPI_KAM\KPI_KAM.exe --fixture "tests\fixtures\KPI Трофимов Дмитрий 2026.xlsm" --expected tests\fixtures\trofimov_expected.json --report build\packaging-smoke.json
```

Spec задает `onedir`, имя `KPI_KAM` и запуск GUI без консольного окна.
Проверка запускает **собранный executable** в Qt offscreen, импортирует
книгу Трофимова, явно оставляет неизвестные товары несопоставленными,
проверяет Decimal-результаты по независимому эталону, аудит и SQLite-историю.
Также проверяются новый GUI, внешний прайс, общий файл, SUPPORT calls,
закрытая выплата, поздний возврат, XLSX export и восстановление БД.
Планы проверки — Q1 20 000 000, Q2 10 000 000, Q3/Q4 0; это тестовые планы.
Отчет находится в `build\packaging-smoke.json`. Любая ошибка тестов,
сборки или проверки executable завершает скрипт ненулевым кодом.
Переменные offscreen действуют только внутри скрипта сборки.

Результат:

```text
dist\KPI_KAM\
  KPI_KAM.exe
  _internal\       # Python runtime, Qt DLL, плагины и остальные зависимости
```

Копируйте **всю папку `dist\KPI_KAM`**, затем запускайте `KPI_KAM.exe`.
Отдельный exe без `_internal` работать не будет. Для другой базы данных:

```bat
dist\KPI_KAM\KPI_KAM.exe gui --db "D:\KPI data\kpi_kam.db"
```

По умолчанию база и логи создаются в `%APPDATA%\KPI_KAM`, независимо от
места установки приложения. В дистрибутив не включаются исходные Excel-книги,
тестовые fixtures, пользовательские базы или логи.

## Windows artifact в GitHub Actions

PyInstaller создает executable для платформы, на которой запущен.
Windows executable нужно собирать на Windows; Linux не создает PE/`.exe`
этой конфигурацией. Workflow `.github/workflows/build-windows.yml` использует
`windows-2022`, Python 3.12 x64 и тот же `build_windows.bat`.

После отправки изменений в GitHub сборка запускается при push/PR с изменениями
в `kpi_kam/` или самом workflow. Для ручного запуска выберите **Actions →
Build Windows onedir → Run workflow** и нужную ветку (для появления кнопки
workflow должен быть доступен в default branch).
В успешном запуске скачайте artifact **KPI_KAM-windows-x64-onedir**.
ZIP содержит `KPI_KAM.exe` и `_internal` в корне: извлеките все содержимое
в одну папку, например `KPI_KAM`, и запустите exe. Второй artifact,
**KPI_KAM-windows-build-report**, содержит JSON-отчет проверки executable.
Artifacts хранятся 14 дней; готовый дистрибутив можно хранить локально дольше.

В Linux можно проверить общий spec и зависимости, но результат будет
Linux executable, а не Windows-сборка. Из `kpi_kam`:

```sh

```

## Экраны GUI и права

* **Новый расчет**: импорт общего файла, активная версия внешнего прайса,
  сотрудник, год, сохраненная должность, четыре обязательных плана и звонки
  для сопровождения. Планы звонков Q1–Q4 вводятся вручную, сохраняются по
  сотруднику и году и восстанавливаются после перезапуска. Начальное значение
  750 можно изменить; план должен быть положительным. У оплаченного квартала
  план и факт звонков зафиксированы.
* **Сопоставление**: название + фасовка из общего файла; 200, 500 и 1000 мл
  отображаются отдельными строками и имеют отдельные алиасы. Список прайса
  фильтруется по фасовке; несовместимый объем нельзя подтвердить.
  Отдельная колонка `фасовка` внешнего прайса читается и сохраняется с его
  версией: например, «Латема высокопитательная» с фасовкой `400 г`.
  Одинаковые названия с разными фасовками считаются разными товарами;
  без однозначной фасовки программа предлагает ручное сопоставление.
  Категория берется из текущего внешнего прайса. Явное исключение из зеленой зоны также
  сохраняется с версией прайса; выручка остается в факте.
* **Отгрузки**: месячные события, клиент/тип, raw/canonical product, группа,
  количество, выручка, цена/порог 1 знак, eligibility, лист/строка/контракт.
* **Возвраты**: FIFO allocation, исходный квартал/eligibility/paid, clawback,
  остаток и статус сверки. Администратор может вручную указать исходную продажу.
* **Премия**: план, положительные продажи, возвраты, факт, attainment,
  четыре блока с базами/ставками, звонки, calculated premium, clawback,
  carry, payable и paid. Фактическая сумма редактируется перед подтверждением.
* **Администратор**: salted PBKDF2 login, внешний прайс, сотрудники/алиасы/
  должности по году, KPI settings, XLSX export, backup+двойной reset,
  смена пароля. Начальный пароль: `stopp`. Он не сохраняется
  открытым текстом в БД или логах; сессия не переживает перезапуск.
  При обновлении прежний начальный пароль автоматически заменяется на `stopp`
  после проверки salted hash. Пароль, который пользователь уже изменил,
  сохраняется; его можно поменять в «Смена пароля», указав текущий пароль.
* **История**: неизменяемые snapshots новых расчетов; двойной щелчок открывает
  сохраненный прайс, ставки и события. «Старая история» открывает прежний формат.

Обычный пользователь может импортировать продажи, сохранить планы и звонки,
сопоставить товары, рассчитать премию, просмотреть историю и подтвердить выплату.
Импорт прайса, сотрудники/роли, настройки, экспорт, сброс и смена пароля
проверяют admin-сессию на уровне сервиса, а не только кнопок.

XLSX-экспорт одного или всех сотрудников сохраняет суммы числовыми ячейками,
округленными HALF_UP до одного знака после запятой. Для денег используется
русский формат `[$-419]0.0`, для процентов — `[$-419]0.0%`; Excel отображает
десятичную запятую. Проценты записываются числовыми долями (например, `0.933`
показывается как `93,3%`), количества и число звонков также остаются числами.
Названия и реквизиты сохраняются буквальным текстом. Результаты ядра и снимки
в SQLite сохраняют исходную Decimal-точность; округление применяется к экспорту.

БД мигрирует добавлением таблиц и nullable-полей прежней `calculations`.
Перед обновлением схемы существующей непустой БД автоматически создается backup.
`schema_version=2` добавляет `price_products.packaging` к первой нумерованной
миграции; старый формат не имел schema_version. Новые snapshots имеют payload version 2, старые version 1 читаются
без изменения. После выплаты SQLite защищает расчет и payment record от UPDATE.
Прайсы версионированы, их продукты не изменяются UPDATE.

Данные по умолчанию: `%APPDATA%\KPI_KAM\kpi_kam.db`, `logs\app.log` и
`backups\` на Windows. На Linux — `$XDG_DATA_HOME/KPI_KAM` или
`~/.local/share/KPI_KAM`. С `gui --db PATH` файлы лежат рядом с выбранной БД.
Все финансовые значения — Decimal; SQLite/snapshots сохраняют их с полной
точностью, XLSX export — числами с округлением для отображения. В виджетах нет расчетных формул.
Excel читается в QThread, SQLite остается в основном потоке.

Для Linux/CI без дисплея:

```sh
# Ubuntu/Debian: системные библиотеки Qt не входят в pip-пакет PySide6.
sudo apt-get update
sudo apt-get install --yes --no-install-recommends libegl1 libgl1 libopengl0 libxkbcommon0
QT_QPA_PLATFORM=offscreen XDG_CACHE_HOME=/tmp/kpi-kam-cache .venv/bin/python -m pytest -q
```

`offscreen` позволяет тестировать GUI без дисплея, но Qt всё равно загружает
системные EGL/OpenGL-библиотеки. Ошибка `libEGL.so.1: cannot open shared object
file` означает, что нужно установить пакет `libegl1`. Linux workflow
устанавливает эти пакеты перед Python-зависимостями и тестами.

Для обычного desktop-запуска переменная `QT_QPA_PLATFORM=offscreen` не нужна.
PySide6 устанавливается вместе с требованиями; Microsoft Excel и интернет
во время работы приложения не требуются. GUI-тесты не пропускаются и
проверяют реальные сигналы/виджеты Qt, асинхронный импорт и сохранение истории.

## Прежний формат: импорт и расчет через CLI

Из каталога `kpi_kam` (для Windows используйте свой путь к python):

```sh
.venv/bin/python main.py check "tests/fixtures/KPI Трофимов Дмитрий 2026.xlsm"
.venv/bin/python main.py calculate "tests/fixtures/KPI Трофимов Дмитрий 2026.xlsm" \
  --plans 20000000 10000000 0 0 --leave-all-unmatched
```

Это тестовые планы, не реальные планы сотрудника. Последний флаг — явное
разрешение оставить все оставшиеся неизвестные товары несопоставленными.
Без решений по всем таким товарам расчет блокируется. Можно принять решение
для конкретного имени (`--leave-unmatched "Имя"`) или пустого названия
в конкретной строке (`--leave-row 103`). Они остаются в аудите, их выручка
в корректном квартале входит в факт плана.

Явное сопоставление по имени товара текущего прайса:

```sh
.venv/bin/python main.py calculate input.xlsx --plans 1000 1000 1000 1000 \
  --map "Старое имя" "Имя из прайса" --db data/kpi_kam.db --remember-mappings
```

`--map-row 103 "Имя из прайса"` позволяет выбрать товар для строки без
названия. Решения для одинаковых непустых нормализованных названий относятся
ко всем строкам этого товара. Пустые названия всегда решаются отдельно;
их нельзя запоминать как общий алиас. `--remember-mappings` требует `--db`.
Без `--remember-mappings` выбор действует только в данном импорте.
При следующем запуске с тем же `--db` сохраненные алиасы применяются автоматически.
CLI без `--db` работает без сохраненного каталога и алиасов.

`check` выводит листы, исходное/прочитанное число строк, количество товаров,
ошибки с листом/строкой/полем, неизвестные товары и статус допуска к расчету.
Код 0 означает успешную проверку структуры; незавершенные сопоставления
показаны явно. Ошибка структуры, файлового ввода или расчета дает код 2.
Все четыре плана для `calculate` обязательны и задаются пользователем.
Лист KPI не используется для импорта ни планов, ни результатов.

## Прежний формат: API импорта и сопоставлений

```python
from app.services.excel_importer import import_excel
from app.services.mapping_service import ImportSession
from app.repositories.alias_repository import AliasRepository
from app.models.domain import Plans

imported = import_excel("input.xlsm")
# На Windows без аргумента путь: %APPDATA%\KPI_KAM\kpi_kam.db.
# На Linux: $XDG_DATA_HOME/KPI_KAM/kpi_kam.db или ~/.local/share/KPI_KAM/.
with AliasRepository() as repository:
    session = ImportSession(imported, repository)
    report = session.validation
    # Пользователь выбирает product.id текущего прайса для entry.key:
    # session.select_product(entry.key, product.id, remember=True)
    # Или явно оставляет товар неизвестным:
    # session.leave_unmatched(entry.key)
    # session.calculate разрешён только когда report.can_calculate == True.
    if session.validation.can_calculate:
        result = session.calculate(Plans("1000", "1000", "1000", "1000"))
```

`ExcelImport` сохраняет SHA-256 источника, имена листов и найденные столбцы,
количество исходных строк, исходные номера строк, данные и ошибки. Исходная
книга никогда не перезаписывается; VBA и внешние ссылки не исполняются.
Заголовки ищутся по именам независимо от порядка столбцов и номера строки,
с нормализацией регистра, пробелов/NBSP и ё/е. Требуются все 10 столбцов
отгрузок из ТЗ и четыре столбца прайса; значения дополнительных полей
(клиент/ЮЛ/задача/комментарий) могут быть пустыми. Имена колонок прайса
поддерживают явные варианты «Продукт»/«Номенклатура»/«Наименование продукта»/
«Товар», «Тип продукта»/«Категория»/«Категория продукта» и варианты зеленой зоны.
Пустые строки пропускаются. Отсутствующие/повторяющиеся колонки, неоднозначные
листы, неверные числа, дубли товаров и неподдерживаемые категории блокируют
расчет; некорректная строка не превращается в нулевой оборот. Исходный текст
сохраняется для аудита; нормализация используется при сравнении.

Денежные числа извлекаются из XML непосредственно в Decimal, включая cached
результаты формул. Допустимы текстовые числа с десятичной запятой или точкой,
корректной группировкой тысяч и знаком; даты, bool и нечисловые значения
не принимаются как деньги. Неизвестный период/тип клиента, отсутствующий порог
и невозможность определить цену отмечаются отдельно и остаются исключениями
в расчетном аудите. Неразрешенное сопоставление требует решения независимо
от остальных ошибок строки.

Id товара детерминирован по нормализованному каноническому названию;
перестановка строк/пробелов/регистра прайса не ломает алиас. Существенное
переименование товара требует явного нового сопоставления. Категория/цена
всегда берутся из текущего импортированного прайса, даже для сохраненного алиаса.
Если его товар отсутствует, алиас сохраняется в SQLite, но не применяется:
отчет отмечает `stale_alias`, и пользователь должен принять решение.
Изменения записываются транзакционно; суммы хранятся как текст Decimal.
Ошибочный импорт не заменяет сохраненный каталог. Результаты прошлых расчетов
остаются неизменяемыми; GUI сохраняет полную SQLite-историю отдельными снимками.

## API

```python
from decimal import Decimal
from app.models.domain import Plans, Product, Shipment, Rules
from app.services.calculation_engine import calculate_kpi

products = [Product("p1", "Товар", "СБКС", Decimal("100"), Decimal("100"))]
shipments = [Shipment(3, "1 кв.", "ЛПУ", "Товар", Decimal("10"),
                      Decimal("1000"), Decimal("100"))]
result = calculate_kpi(
    shipments, products,
    plans=Plans("1000", "1000", "1000", "1000"),
    rules=Rules(),
    paid_history={1: Decimal("0"), 2: Decimal("0"), 3: Decimal("0")},
    aliases={"старое имя": "p1"},
)
```

Один вызов соответствует одному сотруднику/году; вызывающий код отвечает за
разделение импортов. `source_row` уникален в рамках импорта. Все четыре плана
обязательны и неотрицательны. Деньги допускают Decimal, строку или int, но
никогда float, bool, NaN или Infinity. Профиль хранит доли: `0.90 = 90%`.
Планы, правила, денежные итоги, продукты и исходные строки сохраняются в
неизменяемом результате и снимке истории.

* Категория и порог берутся из переданного текущего прайса. Неизвестные/похожие
  названия не угадываются. Точный матч имеет приоритет над явным алиасом.
  Неоднозначный прайс и алиас на отсутствующий id вызывают ошибку ввода.
* Цена сравнивается после ROUND_HALF_UP до 0.1. Равенство проходит.
  При отсутствующей/нулевой цене используется выручка / количество.
* Все строки корректного квартала входят в факт, независимо от сопоставления,
  типа клиента, порога и цены. Неверный квартал остаётся только в аудите.
* Для нескольких ошибок строки показывается первая причина в порядке:
  период, тип клиента, продукт, определение цены, порог, цена ниже порога.
  Все доступные поля аудита сохраняются даже для исключённых строк.
* Обороты возвратов учитываются со знаком, финансовые промежуточные значения
  не округляются до копеек. Контекст расчёта — 50 значащих цифр, изолирован
  от глобального Decimal-контекста. Денежное представление округляется
  до копеек только в `format_money`. Выплата не может стать отрицательной.
* Без `paid_history` предполагается, что разрешённые квартальным порогом
  суммы Q1–Q3 были выплачены. Явный словарь означает реальные выплаты;
  отсутствующие ключи равны нулю. При выполненном годовом плане Q4 получает
  `max(0, годовая расчетная премия − реальные выплаты Q1–Q3)`.
  `annual_payable` — реальные выплаты Q1–Q3 плюс новая выплата Q4;
  при переплате прошлого периода он может превышать расчетную годовую премию.
* При нулевом плане процент выполнения не определён (`None`), а порог
  проверяется как обычно (`actual >= 0`).

В `quarters` есть базы/ставки/премии четырёх блоков и исходные номера строк,
план, факт, порог, расчётная и выплачиваемая премии. `audit` содержит исходную
строку, нормализованный квартал/клиента, продукт прайса, вид сопоставления,
сырые и округлённые цены, дельту, блок и причину исключения.
`green_totals` содержит все 40 сочетаний квартал/тип клиента/категория.
`actual_source_rows`, `included_rows`, `excluded_rows` обеспечивают drill-down.

Импорт продажи сам по себе не создает выплат. Каждый пересчет — новый snapshot.
Return event hash/ledger предотвращает повторное проведение при повторном импорте.
Ошибки структуры не заменяют успешный импорт. Возврат без источника уменьшает
факт, остается в сверке и не создает автоматической премиальной корректировки.

с ручным планом по каждому кварталу (начальное значение 750), максимум 30000,
gate 90%. Shipment gate 90% блокирует также
выплату звонков. Цена и порог округляются HALF_UP до 0.1, равенство проходит.
Q4: при годовом gate годовая расчетная премия минус реально paid Q1–Q3,
затем текущий clawback/carry; звонки учитываются один раз. Дополнительное
вычитание прежних удержаний не применяется по явному выбору пользователя.

## Regression fixture и ограничения

См. `tests/fixtures/README.md`. Workbook используется только в тестах.
Тестовый XML-адаптер сохранён как независимый путь проверки. Тот же эталон
проверяет production-импортёр и ImportSession; GUI-тесты проходят полный путь
от проверки файла до расчета/истории на этой книге. Новый XLSX export использует snapshots общего файла продаж. Windows onedir
собирается и проверяется через GitHub Actions.
Логи CLI выводятся в stderr; GUI сохраняет
вращаемый app.log рядом с базой данных, без названий клиентов.
GUI проверен настоящими Qt-виджетами в Linux offscreen, включая event loop
desktop entry point. Windows-native запуск/сборка в этой среде не выполнялись.
Входные формулы не вычисляются: импорт использует сохранённые результаты.
При отсутствии результата формулы количества/выручки расчет блокируется;
при отсутствии цены применяется revenue/quantity; отсутствующий порог дает
исключение из зеленого коридора. Отсутствующие cached значения всегда
отмечены в отчете. Файлы .xls, зашифрованные и поврежденные книги не поддерживаются.
