# Переход на общий файл продаж

Существующие `Shipment`, Decimal calculation engine, product matcher, XML-числа,
SQLite-алиасы, снимки версии 1 и PySide6-представления сохраняются.
Новая оркестрация добавляется поверх этих компонентов, без пересоздания БД.

1. Зафиксировать тестами клиентский тип, динамические месяцы/возвраты,
   внешнюю категорию, роли, звонки, выплаты и возвраты до/после выплаты.
2. Миграция версии 1: расширить сотрудников; добавить aliases, year profiles,
   role templates, price versions/products, sales imports/contract lines/events,
   return allocations/ledger, payments, admin credentials и settings.
   Дополнительные поля `calculations` nullable для старых снимков.
   Перед первой миграцией существующей непустой БД — SQLite backup.
   Миграции выполняются транзакционно и повторный запуск безопасен.
3. Общий sales parser читает только два контрактных листа. Встроенный прайс
   игнорируется. Excel-даты и группы возвратов находятся в первых 30 строках;
   денежные XML-токены читаются непосредственно в Decimal. Ошибки сохраняют
   номер листа/строки. Неизвестные сотрудники и товары требуют решения.
4. Внешний прайс импортируется только в admin-сессии; каждый импорт создает
   новую неизменяемую версию. Старые snapshots/version 1 не переписываются.
5. FIFO учитывает оставшуюся исходную отгрузку. Первоначальный paid status,
   категория, eligibility, роль/ставка сохраняются в allocation. До выплаты
   уменьшается исходная база; после выплаты создается отдельный clawback.
   Факт уменьшается в месяце возврата. Пересчет не является денежной проводкой:
   ledger уникален, подтверждение выплаты атомарно, повторный импорт не
   применяет возврат еще раз. Излишек clawback переносится вперед.
   Возврат следующего года по неоплаченному исходному периоду создает
   новый исправленный snapshot прошлого года вместе с текущим расчетом,
   в одной SQLite-транзакции. Закрытые периоды не переписываются.
6. KAM/SUPPORT используют общее ядро аудита и отдельную тестируемую политику.
   Фактические платежи используются для Q4; calls учитываются ровно один раз.
7. После прохождения тестов сервисов — расширить существующую GUI оболочку:
   основной workflow, месячные события, возвраты, выплаты и admin tabs.
   Старую историю оставить доступной. Добавить XLSX export из snapshots.
8. Выполнить весь pytest, проверку реального frozen процесса и Windows CI.

Особенности приложенных файлов: в листе «контракты ЭП» нет обязательной
строки метаданных. Импорт требует явного подтверждения полей этого листа,
не переносит буквы колонок из другого листа автоматически. Возвраты без
подписей единиц представлены двумя одинаковыми соседними заголовками:
первый — количество, второй — сумма. В файле встречаются менеджеры Тендер,
Бабенкова — ее строки требуют явного сопоставления. Филимонова Анна добавлена
в начальный каталог с алиасом Филимонова. По уточнению пользователя строки
с менеджером «Тендер» исключаются, количество видно в отчете импорта.

Уточнение Q4: применяется формула из ТЗ буквально — годовая расчетная премия
минус фактические выплаты Q1–Q3, затем clawback текущего периода/остаток.
Дополнительное вычитание уже удержанных корректировок Q2/Q3 не применяется
по явному выбору пользователя.

В старых KPI-файлах Пермяковой/Гайдиной есть строки шаблона с метаданными
и пустыми количеством/суммой. Regression adapter выделяет реальные денежные
строки; production common parser создает события только для ненулевых пар.
VBA и формулы не исполняются. Планов из Excel приложение не импортирует.

## Учет фасовки

Схема SQLite остается версии 1: дополнительные данные сохраняются в уже
существующих JSON-полях событий и импорта. В события добавлены `packaging`
и `legacy_line_key`, в `SheetLayout` — `packaging_unit`. При чтении старых
снимков отсутствующие поля получают пустые значения; остальные поля снимка
по-прежнему проверяются строго. Снимки закрытых расчетов не переписываются.

Новые идентификаторы контрактных строк и событий включают фасовку, поэтому
перестановка разных объемов в Excel не меняет принадлежность событий.
Первый импорт с фасовкой сохраняет идентификаторы ранее импортированных
строк, обогащая только метаданные событий. Подтвержденные выплаты сохраняются.
Изменение фасовки уже оплаченной отгрузки требует сверки исходного файла.
Алиасы и решения об исключении теперь сохраняются для названия + фасовки;
прежние алиасы остаются в БД и работают для источников без отдельной фасовки.

Начальный пароль обновлен на `stopp`. При первом запуске обновления прежний
начальный пароль заменяется после PBKDF2-проверки; пользовательские пароли
сохраняются. Маркер обновления в `admin_settings` делает переход однократным.
Пароли хранятся только в виде salted PBKDF2 hash, сессия остается временной.

## Ручной план звонков и числовой экспорт

Дополнительной миграции БД не требуется: планы звонков уже хранятся в
`employee_year_profiles.calls_plans_json` и снимках расчета. Интерфейс теперь
позволяет вводить планы Q1–Q4; сервис сохраняет их и запрещает изменение
плана оплаченного квартала. Старые значения планов и закрытые снимки читаются
как прежде. Расчетное ядро получает сохраненные планы из профиля.

При экспорте Decimal записывается числом Excel. Денежные значения округляются
до 0.1 HALF_UP; процентные доли до 0.001 и отображаются с одним знаком
после запятой в процентном формате. Исходная точность БД и ядра сохраняется.
